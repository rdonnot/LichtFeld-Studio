# M3 design — train `--hdr` directly from the bracket JPEGs (hdr-architect, 2026-10-28, read on `hdr` @ 24fbb404e)

**Decision.** A separate ~250-line `HdrBracketStage` (exposure → fixed Debevec LUT CRF → saturation gate), NOT a PPISP mode: PPISP's CRF clamps its input to [0,1] (`ppisp_math.cuh:336`) and the Debevec LUT's own input spans [e^{g[0]}, e^{g[255]}] ≈ [0.007, 5] in the plugin's units, so the parametric CRF stage can never precede the LUT; its exposure tensor is reusable only through `project_mean()`/`exposure_mean`, which are the wrong anchor once the seed is absolute (§3). The loss moves to the **LDR domain** (L1+SSIM on CRF(x) vs JPEG/255): no μ-law in the loss, μ-law stays for eval. Radiance units stay the plugin's (`g(128)=0`), so `hdr_scale`, `hdr_color_max`, `init_log_radiance_sh0`, the EXR eval renders, the PLY/viewer contract (M4/M5) are unchanged and the M2 numbers compare directly. The plugin writes a second, self-contained dataset folder; the only loader-side change is a position-wise hold-out.

## 1. Dataset layout — `<out>/brackets/` (plugin; no core loader change)
- `brackets/images/pos_NNN_fK.jpg` → symlink (or copy) of the raw JPEG of position NNN, frame K = 0..n−1 ordered by exposure time ascending. Symlinks keep the APP1 EXIF: the trainer seeds from the JPEG itself via `exif_exposure_ev_for_training_images` (`core/exif.cpp:426-435` → `:396-409` reads APP1 of the training path, `:411-424` falls back to `<root>/images/<name>` — our file IS there). `exposures.json` is not read by the trainer; it is for eval.
- `brackets/sparse/0/{cameras.txt, images.txt, points3D.txt}` — TEXT model: LichtFeld falls back to text when there is no `cameras.bin/images.bin` (`colmap.cpp:4356-4366`, search paths `filesystem_utils.hpp:343-349`); a text model avoids pycolmap 4's rigs/frames when adding images. `cameras.txt` = the proxy model's (one shared camera; the plugin runs SfM with `CameraMode.SINGLE`, `sfm.py:90`). `images.txt`: for each proxy image (id p, pose q,t) and each frame K one entry `IMAGE_ID=10·p+K  QW QX QY QZ TX TY TZ  CAMERA_ID  pos_NNN_fK.jpg`, followed by the proxy image's points2D line copied verbatim (same pose → same observations; the text reader takes the next non-metadata line as points2D, `colmap.cpp:2062-2075`). `points3D.txt` = the proxy model's with every track `image_id` remapped `p → 10·p` (frame 0), so the parallax heuristic at `colmap.cpp:1732-1740` still finds ≥ 2 views. Source: `pycolmap.Reconstruction(out/'sparse/0').write_text(tmp)` then rewrite.
- `brackets/crf.json` = `<out>/crf.json` + three new keys: `"iso_ref"`, `"fnumber_ref"` (the shoot's median ISO / f-number — the plugin already knows them: `setting_warnings`, `pipeline.py:228`), `"exif_ev_ref": log2(iso_ref / fnumber_ref²)` (= 2.644 for ISO 100 f/4). The LUT's x-axis unit ("1.0 = code 128 after 1 s at iso_ref, fnumber_ref", `exposures.json` `units`) and its EXIF anchor travel in ONE file. `brackets/exposures.json` = v2 + per source `"frame": "pos_NNN_fK.jpg"` (eval joins on it). Positions whose bracket was skipped/flagged are omitted (no pose) — logged.
- uid order: COLMAP image order (`colmap.cpp:2941-2947`); the hold-out sorts by `image_name` (`training_setup.cpp:1000-1004`), position-major by construction.
- **Hold-out by position** (core, small): today every site does `(i % test_every) == 0` over name-sorted images — `training_setup.cpp:1006,1026,1038` and `:1442,1454,1463`, `trainer.cpp:2978-2982`, `dataset.hpp:289`. With 5 frames/position `--test-every 40` would hold out one frame of pos_000/008/… only. Add `DatasetConfig::test_by_position=false` (`parameters.hpp:503` beside `test_every`; CLI `--test-by-position`, bind like `--test-every` `argument_parser.cpp:840,1541,1707,1865`; JSON `parameters.cpp:502,1631,1657`) and one helper `std::vector<bool> eval_mask(const std::vector<std::shared_ptr<Camera>>& name_sorted, int test_every, bool by_position)` in `training_setup.hpp`: `by_position` → key = `image_name` up to its LAST `_` (`pos_000_f3` → `pos_000`), position index j = rank of the key in first-appearance order, eval iff `j % test_every == 0`; else the old `i % test_every`. Replace the 8 inline tests with the mask. `--test-every 8 --test-by-position` on 40 positions = pos_000/008/016/024/032 with ALL their frames — exactly M2's set (M2's `pos_NNN.png` sort gave the same indices). `dataset.hpp:289` (`CameraDataset` without `included_images`) must take the same mask or `test_by_position` in its `DatasetConfig` (`dataset.hpp:232`).

## 2. Units, the scale s, and the loss domain
- **Units**: the plugin's Debevec units. Per-frame absolute log2 gain `b_i = exif_ev_i − exif_ev_ref` (`exif.cpp:313`: `exif_ev = log2(t·ISO/N²)`), so `x_i = v · 2^{b_i}` is "E·t at the reference ISO/N" = the LUT's domain. On the room: `b = log2 t ∈ [−10.6, −2.6]`.
- **Loss in the LDR domain** (recommended): `z = CRF(x_i)`, fused L1+D-SSIM(z, jpeg/255). Why: it compares what the sensor measured, noise-weighted by the CRF's own compression; it needs no s and no μ; `C1/C2` (`ssim.cu:1977,2031`) assume [0,1] — GT is, z is within [−0.2, 1.9] (see extrapolation, §4), fine. Chain gradient on the stored log radiance b: `dL/db = c·2^{b_i}·CRF′(x)·dL/dz = dL/dz · (1/255)/(g[z+1]−g[z])` — the LUT's slope per nat, 0.05–0.5 across the curve, the same order as the μ-law's 0.117 (PLAN M2): self-conditioning kept. A μ-law-domain loss would need x = v/s PER FRAME after exposure and would weight the clipped +4 EV frames like the others — rejected.
- **s on brackets** (`Trainer::measure_hdr_scale`, `trainer.cpp:2826-2862`, new sibling `measure_hdr_scale_brackets`): over ≤ 16 training JPEGs spread across the set, pixels with `5 < z < 250` in all channels, `E = exp(g_c[z]) / 2^{b_i}`, luminance P99 → s. Expect ≈ the M1 merge's 2421 on `smoke_hdr` (the merge's P99 is the same statistic plus lower-bound pixels); assert within 25 % in the smoke test. Written back as today (`trainer.cpp:3051-3060`), `hdr_color_max = 1000·s` (`:3062-3069`) and `init_log_radiance_sh0` (`:2868`, `:3101-3102`) unchanged, `set_hdr` (`:3106`) unchanged.
- μ-law (`kernels/hdr_mulaw.cu`) is no longer applied to GT (`trainer.cpp:6392-6396`: guard with `!hdr_brackets`) nor to the render (`:7248-7251`) in bracket mode; it stays for `--hdr` on EXRs and for the eval tooling.

## 3. Exposure model — `g_i = 2^{b_i + δ_i}`, b_i constant from EXIF, δ_i learnable (default) or frozen
- Keep the learnable part a DELTA around the absolute EXIF gain: `b_i` lives in a constant tensor, `δ_i` (init 0) is the parameter. Then the scale ambiguity (radiance ×2^a, all δ −a) is pinned by the prior `λ Σ δ_i²` toward the EXIF — which is exactly the anchor we want (the data's absolute units), unlike PPISP's `exposure_mean` smooth-L1 on the mean (`ppisp.cpp:833-839`) + `project_mean()` (`:1170-1182`) which pin the MEAN to 0 and would fight an absolute seed; PPISP's `clamp(0.5·(ev−mean), ±16)` seed (`trainer.cpp:1283-1315`, `ppisp.cpp:213`) and the ±16 EV clamp (`ppisp_math.cuh:159-160,179-181`) are irrelevant to δ (clamp δ at `±hdr_exposure_max_delta = 3` EV; real EXIF is within ±0.3 stop).
- Flag `--hdr-exposure exif|learn` (default `learn`; `exif` = δ frozen at 0). Prior `hdr_exposure_prior = 1.0` (loss += λ·mean_i δ_i² over the frames seen this step; per-pixel photometric gradients on δ are O(0.1) after the mean over pixels, 2λδ = 0.2 at δ = 0.1 stop — pinned to ~0.1 stop unless the data insists). Adam, `hdr_exposure_lr = 2e-3` (= `ppisp_lr`), no warm-up. Synthetic EXIF is exact: `learn` must not score below `exif`; if it does the prior is too weak (table in §6 runs both).
- Component `src/training/components/hdr_bracket_stage.{hpp,cpp}` + `kernels/hdr_bracket.cu` (~250 lines): `register_frame(uid, b)`, `finalize()`, `apply(v, uid, gt) → z` (saves `x_i` and the gate mask), `backward_in_place(grad, uid)` (grad_v = grad_z·dz/dx·2^{b+δ}; accumulates `dδ_i = Σ grad_z · dz/du · ln2`, see §4), `step()` (Adam on δ + prior), `delta(uid)` for eval/log, `apply_eval(v, b)` (δ = 0, for held-out frames — mirrors `trainer.cpp:9931-9941` where held-out frames get EXIF exposure), serialize/deserialize into the checkpoint beside PPISP's (`trainer.cpp` resume path), `log_eval_diagnostics()` (mean/max |δ|, gate fractions). dδ reduction: per-pixel atomics into one float per frame are fine at these sizes (or a cub block reduce as `ppisp.cu:75-160`).

## 4. The CRF stage — fixed Debevec LUT, per channel
- Load `crf.json` (`log_irradiance[3][256]`, `exif_ev_ref`) at `Trainer::initialize` (nlohmann is already used in `parameters.cpp`); make each `g_c` strictly increasing exactly as `hdr_metrics.py:63-67` (`maximum.accumulate` + `1e-12·z` ramp) so core and tools agree; upload `g[3][256]` and the end slopes to the GPU.
- Forward, per channel: `u = ln(max(x, 1e-12))`, clamp `u ≥ g[0] − 5`; segment search `g[k] ≤ u < g[k+1]` (binary search over 256, or a 1024-bin inverse table on a uniform u grid between g[0] and g[255] — either is O(1) per pixel); `z_f = k + (u − g[k])/(g[k+1] − g[k])`; `z = z_f / 255`. **Beyond the ends extrapolate linearly in u with the end segment's slope — never clamp z**: a flat clamp would give a stuck zero gradient to any pixel the render puts above the LUT while the JPEG is < 250 (z up to ≈ 1.9 at the radiance cap; down to ≈ −0.2 at `u = g[0] − 5`).
- Backward: `dz/du = (1/255)/(g[k+1] − g[k])` (the end slopes outside), `dz/dv = dz/du · (1/x) · 2^{b+δ} = dz/du / v`, `dz/dδ = dz/du · ln 2` (independent of the magnitude of x). Save `k` (uint8) and `u`'s validity per pixel-channel in the forward; the backward reads the saved `x` (as `hdr_x_saved` does today, `trainer.cpp:7204`).
- **Saturation gate** (this is where the lamp is recovered): the JPEG at `z_gt ≥ 250/255` only says `x ≥ x_250`; at `z_gt ≤ 5/255` only `x ≤ x_5` (noise floor, JPEG black crush). Fold a one-sided loss into the prediction: `z' = min(z, z_gt)` where gt is clipped high, `z' = max(z, z_gt)` where clipped low, identity elsewhere; backward mask 1 where unclamped, 0 where clamped. This is exactly the one-sided L1 and the SSIM sees a consistent image; it costs no change to the fused kernel. Zero weight is rejected: the lamp (truth ≈ 372, clipped in every frame) would be unconstrained from below and could settle anywhere; the gate keeps it ≥ the brightest frame's bound (and no more — the μ-law-vs-truth metric will show that residual; `hdr_metrics.ldr_psnr_at_exposure` masks the same pixels, `hdr_metrics.py:84-87`). Log the gated fraction per EV once at startup (+4 EV ≈ 40 %, −4 EV mostly the low gate).
- **Parametric alternative** `--hdr-crf ppisp` (second stage, optional): `f(x) = (1−e^{−3x^{0.75}})/(1−e^{−3})` is a concave curve with infinite slope at 0 and f(0.5) = 0.876; PPISP's piecewise power (`ppisp_math.cuh:351-363`: `a(x/c)^toe` then `1 − b((1−x)/(1−c))^shoulder`, then `^gamma`, toe/shoulder ≥ 0.3, gamma ≥ 0.1) is NOT the same family but approximates it to ~1–2/255 when seeded by a least-squares fit (c ≈ 0.1, toe ≈ 0.75, shoulder ≈ 2, gamma ≈ 1) — fine for real cameras where the Debevec curve is noisy, inferior to the exact LUT on the synthetic set. Mechanics if built: scale `x_sensor = x / e^{g[255]}` (full well = 1 in PPISP's domain), call PPISP's camera stages only — the kernels already skip exposure and colour when `frame_idx == −1` (`ppisp.cu:51-66`, backward `:110-151`), so a 20-line `PPISP::apply_camera_stages / backward_camera_stages(rgb, camera_id)` wrapper suffices; vignetting comes for free (identity init `ppisp.cu:446-470`, learnable — correct place for it, before the CRF); trainer step reuses `ppisp_->reg_loss_gpu/optimizer_step` at `trainer.cpp:8246-8255` without `project_mean`. Not needed for the Done-when.

## 5. Gradient chain, SSIM, densification

Backward: `stage.backward_in_place(raster_grad, uid)` replaces `hdr_mulaw_backward_` at `:8004-8008`; `stage.step()` after the PPISP block (`:8240-8256`), skipped in POPSpa like `ppisp_frozen` (`:6438`). The SSIM/CS error map, edge map, thin-structure map and the MRNF/MCMC `blending_weight · pixel_error` accumulation read `z` and `gt` — dimensionless in [0,1], so `growth_grad_threshold` keeps its meaning (same argument as PLAN M2). 5× the images changes nothing per iteration (schedules are iteration-based); each position is still visited 7000/40 times, each frame 1/5 of that. Owed from M2 and cheap here: dump the `_refine_weight_max` histogram once (LDR vs HDR-EXR vs brackets) in the smoke run. ## 8. Risks, in the order I expect them to bite
1. **Unit/anchor mismatch** (`exif_ev_ref` wrong or missing → a 2^2.64 = 6.25× error): detect at load — s from brackets must be within 25 % of the M1 merge's 2421 on `smoke_hdr`, and `bracket_eval.py`'s fitted gain must be ≈ 1.
2. **Gate sign or coverage wrong**: the +4 EV frames are ~40 % clipped (the 92.7 %-clipped frame per PLAN M1) — a wrong gate either kills the lamp or lets the sky drift. Check: gated fractions per EV at startup, and `max rendered radiance` ≥ 15 000 at 3000 it as in M2.
3. **Scale drift under `learn`**: all δ sliding together against radiance. Monitor mean δ each eval (`log_eval_diagnostics`); |mean δ| > 0.1 stop on synthetic data = prior too weak; the `exif` run is the control.
4. **Dead gradients at the LUT ends** if someone clamps z — covered by the extrapolation; a gtest checks dz/dv ≠ 0 for x beyond both ends.
5. **−4 EV noise / JPEG blocking in the dark frames**: L1 is robust and the low gate removes the floor; expect this EV's PSNR to be the lowest and say so if the mean passes on the other four.
6. **LDR bit-identity**: everything is behind `hdr_brackets`; `ldr_reeval.py` identical twice is the proof, as every milestone.
7. **Real captures later**: a non-zero MTB `shift` means the pose is NOT shared — a frame with a shift needs its own camera entry with the principal point offset by (−dx, −dy) (one `cameras.txt` line per shifted frame); ghosting is still the merge path's problem (M1). Not needed on the tripod set (all shifts 0).
